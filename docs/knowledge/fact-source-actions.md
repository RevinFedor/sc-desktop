# Knowledge: Source actions — единый паттерн action-row

Описывает **как устроены кнопки на странице источника** во всех платформах одинаково. Mental model:

> Action-row — это пульт страницы источника. Все операции над ним (cheap-stats / fetch / assemble / pick) — toggle inline-блоков под action-row, не push отдельного screen. Все кнопки рендерятся через `<ToolbarButton variant=…>` — единая высота `h-9`, разница только в варианте (neutral / primary / accent).

## 🎛 Сущности

| # | Кнопка | variant | Что делает | Когда видна |
|---|---|---|---|---|
| 1 | **📊 Обзор** | neutral | inline-блок с глобальной сводкой по источнику | если у платформы есть **дешёвый, fetch-independent** способ её получить |
| 2 | **⚙ Новый запрос…** | primary | inline-форма с параметрами; submit запускает fetch-job | всегда |
| 3 | **📋 Скопировать · N** | neutral | inline assemble-панель (CopySavedPanel) — собрать срез сохранённого в clipboard / .txt | TG-only, при `totalItems > 0` |
| 4 | **⚙ Picker** | neutral | inline-список items с чекбоксами для batch-операций | если у источника есть batch-операция (транскрипция) |
| 5 | **🧠 Проиндексировать (full\|N)** | accent (emerald) | запускает векторный индекс по сообщениям (Gemini embeddings → `items_vec`) | Telegram only, прижата к правому краю action-row |

Скрытые кнопки **не рендерятся серыми/disabled** — нет смысла = нет кнопки. Юзер не должен думать «почему оно недоступно».

## 🧱 ToolbarButton — единый стилевой контракт

Все 4-5 кнопок action-row создаются через `<ToolbarButton variant active onClick title>`. Это снимает три проблемы старого кода:
- **высоты разъезжались** — у «Новый запрос» был `py-2` (~36px+padding), у «Проиндексировать» `h-9` (36px ровно), визуально не в одну линию
- **font-medium только на одной кнопке** — белая «жирная» «Новый запрос» выглядела «другой лиги», что не соответствовало семантике (это та же операция уровня кнопки, просто primary)
- **легко добавить новую** — `<ToolbarButton variant="neutral">` без локального копирования tailwind-класс-супа

Варианты:
- `neutral` — text-on-hover-bg; `active=true` → solid `bg-zinc-800` (для toggle-кнопок что показывают раскрытое состояние)
- `primary` — outlined `border-zinc-600 + text-zinc-100`, без bold; `active` → `bg-zinc-800` (та же визуальная масса как neutral в open-state — пользователь видит что «открыта»)
- `accent` — emerald (`bg-emerald-700 hover:600`); используется только для длительных commit-операций (Проиндексировать)

`active` отделён от `variant` намеренно — каждый variant имеет свой active-вид. Если бы свернули в один enum получилось бы 6 значений (`neutral`/`neutral-active`/`primary`/`primary-active`/…), будущие callers не знают существует ли `primary-active`.

## 🎬 Boosty: полный каталог и рабочий список — разные режимы

У Boosty кнопка «Обновить весь каталог» и форма «Новый запрос…» не дублируют
друг друга. Первая всегда читает неограниченную нефильтрованную ленту и может
подтвердить, что источник покрыт целиком. Вторая делает только scoped-проход
(лимит, направление, даты, тег, «только доступные мне»): она добавляет известные
посты, но не имеет права заменить уже подтверждённое покрытие ленты частичным
результатом.

Поэтому вместо отдельного `Обзора` над списком всегда остаётся строка охвата:
она отвечает «вся ли лента известна» до и после изменения формы. Picker тоже не
прячется в inline-панель: список постов сам является рабочим местом для фильтра
«аудио на диске», сортировки по весу и раскрытия нескольких видео одного поста.
Чекбокс родителя выбирает его детей, а не создаёт второй плоский каталог.

Запрос каталога сохраняет только текст, метаданные, доступность и ссылки на
плееры; скачивание MP3 и расшифровка — отдельные явные действия выбранных
видео. Полный протокол — `fact-boosty.md`.

## 🎯 Правило для «📊 Обзор»

> Кнопка имеет смысл **только** когда показываемые цифры **не зависят** от того, что юзер собирается фетчить.

- IG `web_profile_info` отдаёт `media_count`, `follower_count`, `biography` — те же значения независимо от того, парсит юзер `last_n=50` или `all`. → Отдельная кнопка, контент не повторяется в форме.
- TG pre-analysis (`--preview-only`) считает `type_counts`, `senders`, `date_min/max` для **выбранного** диапазона. Поменял `last_n` → должен поменяться обзор. → Живёт **внутри** формы рядом с инпутами параметров. Делать его отдельной кнопкой = хардкодить один диапазон и сломать детерминированность («юзер видит обзор не того что собирается фетчить»).
- TG локальная оценка сохранённого диапазона тоже живёт **внутри** формы, но это не замена pre-analysis. Она пересчитывается от уже сохранённых items при смене диапазона/типов и показывает числа прямо в строках чекбоксов: «Видео 8 · 4:01», «Фото 70». Summary обязан говорить «по сохранённому диапазону», потому что источник данных — локальная библиотека, а не live Telegram.
- Переключение чекбокса типа **не** пересчитывает локальную оценку: breakdown уже содержит все типы текущего диапазона. Пересчёт нужен при смене диапазона/source/topic; spinner в поповере показывается только на выбранных строках, чтобы клик по «Видео» не превращал все пять типов в loaders.
- YT/TK `yt-dlp --flat-playlist` — это уже full fetch. Нет «бесплатной сводки». Stats-карточки наверху SourceDetail (`Сохранено N · Период min — max`) показывают всё что мы знаем по уже спарсенному. → Отдельная кнопка не нужна.

**Тест:** если результат «обзора» поменяется при изменении любого инпута в форме «Новый запрос» — обзор живёт **в форме**, не отдельно.

## 🧠 Правило для «🧠 Проиндексировать» (4-я сущность)

Не форма а **прижатая к правому краю** кнопка с выезжающим chevron-input
для лимита (`◀ full|N`). Почему не отдельная форма как «Новый запрос»:

- индексация не зависит от диапазона дат / типов / отправителей — есть
  ровно один параметр (`limit` от свежих, опциональный) и ровно одна
  кнопка submit
- единственный chevron-input решает refinement параметра — высота строки
  не меняется, контекст action-row не разрушается дополнительной формой
- статус («сейчас 3000/9484, 32%») живёт в `CoverageBars` снизу, не
  в самой кнопке — кнопка остаётся обещанием действия

Подробности (когда стоит индексировать, кумулятивный прогресс, внешний
RPM-лимит Gemini, MCP-тулзы для Claude Code) — `fact-semantic-search.md`.

Когда `tg:indexStatus` показывает `done >= total` и `total > 0`, кнопка
переходит в terminal state «Индекс готов» и disabled. Повторный клик не
должен уходить в backend «проверить на всякий случай»: на реальном чате
55k это выглядело как дикий лаг при клике по индексации, хотя видимой
работы индекса уже не было.

## 💬 «Дотянуть комментарии» — conditional 5-я сущность (TG)

Кнопка `💬 Дотянуть комментарии (M)` появляется **только** когда:
- `s.platform === 'telegram'`
- `s.has_discussion === 1` (linked discussion group подтверждена при предыдущем
  fetch'е через `GetFullChannelRequest`)
- `posts_count > postsWithComments` (есть хотя бы один пост в БД, у которого
  ни одного коммента ещё нет)

Не toggle-блок (как у трёх основных кнопок) — а одно-кликовый job-spawn
сразу. Дополнительный inline-form не нужен, дефолт «все комменты на пост»
покрывает 95% юзкейсов; кому надо лимит — пусть откроет «Новый запрос…»
с чекбоксом «Комментарии» включённым.

Click → собирает `missing = items.external_id - listPostsWithComments` и
передаёт в `tg:catchUpComments` IPC. Подробнее `fact-telegram-comments.md`.

> **Почему не объединить с «Новый запрос…».** «Новый запрос» = re-walk
> сообщений + заново все комменты к ним. «Дотянуть» = пропустить сообщения
> вообще, идти только за комментами по post_ids которые уже в items table.
> Юзер на 5k-канале не хочет ждать 5 минут iter_messages чтобы дотянуть
> комменты к свежим 50 постам.

## 🪞 Без дублей кнопок

Раньше action-row содержал две кнопки `▶ Подтянуть свежие` (quick) + `⚙ Новый запрос…` (custom). Это **дубль**: «подтянуть свежие» = «новый запрос с дефолтами». Убрали quick-кнопку, оставили только форму с пред-заполненными дефолтами.

Юзер делает один лишний клик на «открыть форму» — но взамен видит что именно отправит. Детерминированность важнее на одну операцию.

**Старое имя `Sync new` тоже устарело** — юзер не знает какие именно «новые» сообщения и сколько. «Новый запрос…» с открывающейся формой говорит ровно то что произойдёт.

## 🪟 Inline вместо push

Все три кнопки — `useState`-toggle, который раскрывает блок **под** action-row. Не `pushScreen('tg-config', ...)`, не отдельная страница.

**Зачем:**
- Breadcrumb остаётся `Home › @channel`, не уезжает в `Home › @channel › Custom fetch`. Иерархия не теряется.
- Selection в LibrarySidebar не сбрасывается. Юзер видит «я внутри @channel» постоянно, пока работает с формой.
- Stats-карточки и история парсинга остаются над/под формой — контекст не теряется.

**Что отбросили:** старый `tg-config` push-screen из SourceDetail. Он сбрасывал trail (см. `fact-navigation.md::Канонический trail`) и юзер «улетал» в отдельный экран без признаков что он внутри @channel. Inline решает это бесплатно — форма та же (`TelegramConfigForm` headless-компонент), просто рендерится в другом контейнере.

## 🧷 «Скопировать сохранённое» — кнопка action-row (TG)

Раньше панель `📋 Скопировать сохранённое · N` жила под графом
«Распределение по типам» (collapsed-секция). Теперь это полноценная
кнопка action-row рядом с «Новый запрос…» — controlled-prop'ом
(`open` + `onToggle`) `CopySavedPanel` управляется снаружи, header-кнопка
внутри панели в этом режиме не рендерится.

**Почему переехала:** старый mental model «связка с графом сверху»
(увидел распределение → выбрал срез) ломался из-за двух UI-блоков под
графом одновременно (Senders, History) — юзер скроллил вниз искать
панель, не сразу её видел. Действия над источником семантически живут
в одной шеренге: fetch (Новый запрос) и assemble (Скопировать) — обе
operate **на источнике**, не «по разным семантическим уровням».

**Почему не auto-collapse при копи-успехе.** Toast в кнопке (см.
`methodology/переносимый-дизайн.md::Toast в кнопке`) держит юзера в той же сессии —
закрывать панель = терять параметры (range, types) для повторного копи
с другим срезом. Юзер сам жмёт «Скрыть копирование», когда закончил.

YT/IG/TT не получают эту кнопку. У batch-jobs там Combined-файл уже есть
через job-lifecycle (см. `fact-jobs.md::Auto-combined.txt`). Подробнее
о работе панели — `fact-copy-saved.md`.

## 🧬 Shared scope-fields: TelegramScopeFields

Range / Types popover / Topics popover / Comments-toggle живут в одном
presentational-компоненте `<TelegramScopeFields use="fetch|copy">` —
shared между `TelegramConfigForm` (fetch), `CopySavedPanel` (copy) и
`TelegramScreen` (folder-batch, тоже `use="fetch"` + кастомный
`rangeModes`-проп). Контейнеры держат state, scope-fields — только UI.

**Жёсткое правило (см. переносимый-дизайн.md::Параллельные UI-flows):** обе формы
рендерят строки в **одинаковом** порядке и на одинаковых позициях —
«Диапазон» сверху, «Типы контента + Темы» одной строкой ниже. Различия
живут только **внутри** контролов, не в виде «в copy темы перенесены в
отдельную row». Создавать второй компонент под второй flow — почти
всегда баг архитектуры.

Различия по `use`:
- **range modes:** fetch имеет `between` (URL-based; copy этого не
  поддерживает — DB уже не помнит URL отдельных сообщений)
- **engine select:** fetch-only (для voice/video транскрипции); в copy
  всё уже на диске. Живёт *внутри* TelegramTypesPopover как nested-Select
  у строки «Голосовые» — не отдельной строкой формы.
- **comments:** fetch держит «Комментарии» как тип контента в popover'е
  (это что мы качаем) + per-post limit row; copy показывает flat-чекбокс
  «с комментариями» вне popover'а (это формат вывода — вставить тред под
  пост в text-блоб). Несимметрия осмысленная: разная семантика, не разная
  структура формы.
- **topics popover (`TelegramTopicsPopover`):** общий компонент с двумя
  режимами — `mode="multi"` в fetch (чекбоксы, multi-select для пред-фетча),
  `mode="single"` в copy (radio-кнопки + auto-close на выбор, так как
  copy строит срез по одной теме). Визуально chip одинаковый, summary
  «Все темы» при пустом значении.
- **direction toggle (lucide ArrowLeftRight):** copy-only пока — `tg_fetch_json.py`
  не принимает `--reverse`. В copy переключает «N с конца / с начала»
  (`scope.direction = 'newest'|'oldest'` → `assemblyEstimate` + `assemblyFetch`
  меняют `ORDER BY published_at DESC|ASC` под одним LIMIT)

**Type-id mapping:** popover использует `docs` как label-id для
компактности; SQL items.type хранит `document` (Telethon-term, как пишет
`tg_fetch_json.py`). Mapping `docs → document` живёт в `CopySavedPanel`
buildScope, чтобы scope-fields оставался агностичным к downstream-семантике.

> **Антипаттерн (история):** в copy была отдельная `RowLabel «Тема»` со
> своим full-width `<Select>` под Types-row, в fetch — popover-чип рядом
> с Types на той же строке. Один и тот же компонент `TelegramScopeFields`,
> но две разные ветки рендера → два разных visual layout'а для одной мысли
> «фильтр по теме». Удалено в пользу единой строки + `mode` prop'а на
> popover'е.

## 🪺 Сплит-кнопка «Новый запрос…» (TG)

`NewRequestSplitButton` — две зоны в одной обводке: левая (фикс-ширина,
chevron-стикер + константный текст) toggle'ит форму, правая (узкая, Zap)
запускает **догрузку без формы**: `sync_new` от `MAX(external_id)` источника
до сейчас; пустой источник — fallback `last_n=200`. Cmd+hover над кнопкой
показывает tooltip с параметрами, которыми пойдёт быстрый запрос.

**Параметры быстрой зоны = last-used блоб формы.** Правая зона читает тот же
`localStorage['tg-config-form-last']` (через `lib/tgFetchParams.js`), что пишет
`TelegramConfigForm` и читает `SidebarContextMenu` («Запросить до конца»). Три
точки входа в quick-fetch — одна память параметров; настроил форму один раз →
все быстрые пути фетчат тем же набором. Добавляя новый quick-action — читать
оттуда же, не заводить свой селектор.

Но range у правой зоны **не** берётся из last-used. Zap всегда означает
`sync_new` от последнего сохранённого сообщения до сейчас; в tooltip оставлены
только content-types и engine. Full-history/URL/date режимы из формы — one-shot
контекст левого «Нового запроса», не память для быстрой догрузки. Иначе прошлый
`all` превращает следующий «догрузить пару дней» в повторный walk всего чата.

**Почему не «Скрыть форму» свопом текста:** юзер явно просил константный
label + состояние стикером (*«чтобы текст не менялся, при раскрытии добавь
какой-то стикер слева»*) — см. `переносимый-дизайн.md::Anti-jitter`.

## 🚪 Mutex inline-панелей в action-row

«Обзор», «Новый запрос…» и «Скопировать» — взаимоисключающие toggle-кнопки:
открытие любой закрывает две других (см. переносимый-дизайн.md::Взаимоисключающие
inline-панели). Picker вне мьютекса — на YT/TT/IG он и есть основной контент
страницы, закрывать его формой нельзя.

## 📜 История парсинга — серверный LIMIT + «Показать ещё»

`listJobsForSource` отдаёт страницу (20), не всё: у старых чатов сотни jobs.
Ловушка, которую уже ловили: SQL-LIMIT без UI-догрузки делает хвост истории
**недостижимым насовсем** — `max-h-80 overflow-auto` контейнер выглядит как
полный список, но 21-я запись не существует для UI. Кнопка «Показать ещё»
внизу списка докручивает `{id, limit}` в тот же IPC. Правило для любого
нового списка с серверным капом — `переносимый-дизайн.md::Хвост истории`.

## 🧾 «Новый запрос» подтверждает запуск через историю

На SourceDetail submit формы — это не просто локальный spinner в форме. Как
только `tg_fetch` поставлен для уже известного source, форма закрывается или
блокируется, а в «Истории парсинга» этого source должна появиться running-row.
Иначе пользователь видит прежнюю idle-кнопку, кликает ещё раз и получает пачку
дублей в глобальной Activity без видимого объяснения на странице чата.

Backend-контракт для этого — `fact-jobs.md::Pending row на spawn/entity`.

## ⏹ Кнопка Стоп

Live job можно остановить из трёх мест: ActivityPanel (правый paneль),
JobHistoryRow (история парсинга на SourceDetail) и сам JobDetail. Все три
зовут один и тот же IPC `jobs:cancel` — child-process убивается через
SIGTERM, статус flip'ается в `cancelled` через job:update. См.
`fact-jobs.md::Cancel`.

## 🩹 Backfill-aware skipDupes

Если юзер выбрал тип, у которого в БД есть items с пустым `caption`
(например, опросы, сохранённые до появления `--process-polls`) — `skipDupes`
автоматически отключается на этот fetch. Без этого сценарий «выбрал только
опросы → 0 new messages» сбивает: `--since-msgid` отрезает именно те ID,
которые мы хотели бэкфильнуть.

Детектор живёт в `TelegramConfigForm` (см. `backfillTypes`/`needsBackfill`),
читает `items:typeBreakdown` и сравнивает `with_caption < count` для
выбранных типов. Это **тихий guard**, не пользовательское предупреждение:
старый hint «N видео/опросов без тела — достать поля» убрали, потому что он
смешивал внутреннюю DB-терминологию с выбором типа контента, не был привязан к
выбранному диапазону и для медиа выглядел как отдельная непонятная работа.

## 🔄 Mental model paste-flow ↔ SourceDetail-flow — единая

Юзер пастит `@durov` в Home → видит inline `InstagramConfigForm` под Detection. После fetch'а форма заменяется на header + picker. Это поведение **то же**, что на SourceDetail когда юзер открывает существующий источник: header сверху + picker снизу.

Различие только в одном:
- **Paste-flow:** форма приходит первой (источника ещё нет), потом сменяется на header+picker.
- **SourceDetail:** header+picker уже есть постоянно, форма — toggle через кнопку.

Один компонент `InstagramConfigForm` обслуживает обе ситуации. На SourceDetail прокидывается `forceForm` prop, чтобы компонент не пытался автоматически переключиться на header+picker (см. `fact-instagram.md::forceForm prop`).

### Ephemeral paste-flows — без SourceDetail-стороны

Не у всех paste-flow есть SourceDetail-зеркало. Три случая «ad-hoc операции» где
сущности «канал/чат/профиль» нет вообще:

| Тип | Что пастишь | Платформа в detect | Commit (как fetch стартует) | Source создаётся? |
|---|---|---|---|---|
| Local file | `/Users/.../video.mp4` | `'local'` | auto-commit на детекцию | ❌ |
| YouTube search | `?search_query=...` | `'youtube'` (kind=`search`) | auto-commit на детекцию | ❌ |
| YouTube single video | `youtube.com/watch?v=...` | `'youtube'` (kind=`video`) | **chip [видео]** или Enter | ❌ |
| Telegram single message | `t.me/<chat>/<id>` | `'telegram'` (kind=`message`) | **chip [сообщение]** или Enter | ❌ |

Все — одноразовые: «получил результат → положил в буфер/историю → дальше». В
Library не появляются, в sidebar не висят. История доступна через Activity tab и
JobDetail — это и есть «персистентная сторона».

> **Почему YT/TG single требуют explicit commit, а local-file и search — auto-commit.** Разница в **обратимости**. Поставил неправильный путь к файлу или ошибся в search query — paste можно скорректировать, fetch ещё ничего не скачал; нужен только список из yt-dlp. А вот для t.me/X/Y и youtube.com/watch?v=... fetch _сразу_ запускает API-call (Telethon get_messages, yt-dlp transcript-search, скачивание audio). Дать юзеру chip-step — это шанс посмотреть детекцию и абортить до сетевого запроса. Местами симптом бывал: пастил TG-ссылку → input очищался мгновенно → потом Activity показывал «выполнено» с непрочитанным результатом. См. `fact-jobs.md::Voice transcription` про текущий single-flow с двумя стадиями.

**Почему важно для архитектуры:** при добавлении нового paste-input типа задай вопрос
*«это подписка или одноразовый запрос?»*. Подписка → нужен `upsertSource` → SourceDetail
становится главной точкой возврата. Одноразовый → `source_id = NULL`, history-only,
JobDetail-как-final-view (см. `fact-youtube-search.md::JobDetail как финальный read-only
вид`). Не пытаться унифицировать два пути — они **семантически** разные.

См. также `fact-local-files.md`, `fact-youtube-search.md`. Для Telegram single
message — `mode='single'` в `tg_fetch_json.py` + skip `upsertSource` в
`job-runner.js::handleEvent` (см. инлайн-комментарий рядом с `if (!isSingle)`).

## ⚙ Per-platform формы

«⚙ Новый запрос…» раскрывает разное для разных платформ — **по составу параметров**, не по принципу:

- **TG:** `TelegramConfigForm` — самая богатая. Range через `<TelegramScopeFields>` (modes: `last_n` / `last_week`+presets / `from_date` / `date_range` / `between` / `all`), типы контента, движок транскрипции, локальная оценка сохранённого диапазона в чекбоксах типов, **встроенный pre-analysis блок**. `single` убран из формы — single-message делается через Home paste t.me/.../id (см. секцию `Ephemeral paste-flows`).
- **IG:** `InstagramConfigForm` — Reels/Posts чекбоксы, лимит, mention backend в footer (не редактируется здесь — только в IGSettings).
- **YT/TK:** `YouTubeQuickFetchForm` использует `<YouTubeScopeFields>` (`fact-youtube.md::YouTubeScopeFields`) — limit + direction toggle (`--reverse` для oldest-first). Default 50, 0 = весь канал. Date-фильтры невозможны без правки `yt_channel_ndjson.py` (yt-dlp `--playlist-end` режет по count).

Все три — **headless** компоненты без своего header'а / Back-кнопки. Вызывающий контейнер (paste-screen или SourceDetail) даёт ему `<div className="rounded-lg border border-zinc-800 bg-zinc-950 p-6">` обёртку.

## 🚥 Visible feedback на quick-actions

Quick-кнопок (которые делают сетевой запрос без формы) сейчас **не осталось** в action-row. Но раньше для `Sync new` стояло правило «loader минимум 1 секунду» (`Math.max(0, 1000 - elapsed)`) — кеш-хит и реальная работа должны выглядеть одинаково, иначе юзер думает что кнопка ни на что не реагирует. Этот паттерн остаётся валидным для будущих fast-action кнопок (например, «Refresh metadata», «Re-check transcripts»).

См. `methodology/переносимый-дизайн.md::Visible feedback`.

## 🖱 Множественное выделение в сайдбаре + «Запросить до конца»

Второй entry-point для batch-fetch'а помимо TelegramScreen-папок: прямо в
`LibrarySidebar` юзер выделяет несколько Telegram-чатов и правым кликом
запускает догрузку каждого «до конца» (от последнего сохранённого
сообщения до сейчас).

**Выделение только для Telegram.** YouTube/IG/TikTok-строки игнорируют
модификаторы — для них multi-select бессмыслен (операции там
per-source, не batch). Состояние выделения живёт в отдельном
`lib/telegramSelection.js` (не в общем store) — его читают и сайдбар, и
контекстное меню, и оно переживает navigate-away → возврат. Cmd/Shift —
по платформенной конвенции (см. `переносимый-дизайн.md::Множественное
выделение`):
- **Cmd/Ctrl-клик** — тогл одного чата, ставит его якорем.
- **Shift-клик** — диапазон от якоря до текущего по **видимому** порядку
  строк (`tgOrderedIds`: explicit-список + развёрнутое «Прочее», в том же
  порядке что рендерит `PlatformGroup`). Якорь не двигается — повторный
  Shift расширяет от той же точки.
- **Обычный клик** — сбрасывает выделение и открывает чат (старое
  поведение не сломано).
- `pruneTo(visible)` на каждый ререндер выкидывает из выделения id,
  пропавшие из списка (удалили source / свернули «Прочее») — иначе
  Shift-диапазон считал бы по несуществующим строкам.

**Правый клик = replace-if-unselected.** Клик по невыделенной строке
делает её единственным выбором (как Finder/VSCode), по выделенной —
открывает меню для всего выделения. Один пункт `Запросить до конца · N`,
подпись снизу — типы контента.

**Типы берутся из last-used блоба формы**, не из отдельного селектора в
меню: `SidebarContextMenu` читает тот же `localStorage['tg-config-form-last']`
что пишет `TelegramConfigForm` (content + engine). Так юзер один раз
настроил форму в paste-flow → меню фетчит ровно тем же набором, без
дубль-контрола. Если в блобе ни одного типа — пункт disabled с hint'ом.

**Бэкенд — umbrella `tg_catchup`** (см. `fact-fetch-strategies.md::Catch-up
batch` за per-source min_id стратегией и `fact-jobs.md` за lifecycle).
Снапшот переиспользует `tg_folder` shape (та же `FolderRowBody`/JobDetail-
body), маркер различия — `folder_id === null`. После запуска выделение
сбрасывается: job виден в Activity, выделение своё дело сделало.
