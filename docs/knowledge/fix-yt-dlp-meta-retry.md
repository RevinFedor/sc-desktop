# Fix: транзиентный сбой `fetch_meta` (yt-dlp metadata) на первом клике

**Симптом для юзера.** Жмёт `+ ai` (или `copy`) на YouTube-карточке/плеере →
в Активности `✗ error: yt-dlp metadata fetch failed`. Сразу повторяет — на
второй раз всё работает. Характерная сигнатура: **первый `+ ai` падает →
`copy` срабатывает → второй `+ ai` уже ок**. Видео при этом валидное и
доступное.

## Причина

`fetch_meta()` в `python-workers/web/yt_single_ndjson.py` (общий helper, его же
импортит `yt_batch_transcribe_ndjson.py`) — один `yt-dlp --dump-json` запрос
метадаты. Первый холодный вызов после клика **изредка** флакает: YouTube-side
rate-limit, секундный лок `cookies.sqlite` Firefox'а когда два yt-dlp процесса
лезут в куки разом, прогрев nsig/sigfuncs. Точно та же команда на второй
попытке проходит.

**Почему это был чёрный ящик.** Старый код глотал реальную ошибку:
```python
try:
    r = subprocess.run(cmd, ...)
    ...
except Exception:
    return None   # ← вся диагностика потеряна
```
Caller на `None` эмитил безликое `"yt-dlp metadata fetch failed"` — ни кода
выхода, ни stderr yt-dlp. Юзер (и отладчик) видели симптом без причины.

## Решение

1. **Ретрай 3× с линейным backoff** (0.8с, 1.6с). Транзиентный кейс проходит
   со второй попытки за ~0.8с — клик больше не дед-эндит на разовом блипе.
2. **Возвращать `(meta, err)`**, не голый `None`. Реальный stderr/код выхода
   yt-dlp долетает до сообщения в Активности (`yt-dlp exit 1: ERROR: …`),
   следующий сбой уже диагностируем.

Оба caller'а (`yt_single_ndjson.py::main`, `yt_batch_transcribe_ndjson.py::
process_one`) распаковывают tuple и вкладывают реальную причину в emit.

`yt_comments_ndjson.py` держит свою копию `fetch_meta` с тем же ретраем
(её caller деградирует на пустой заголовок видео при `None`, поэтому там
контракт остался single-value — error-строка не нужна).

## Что пробовали и отбросили

Прежде чем добавлять ретрай — воспроизводил точную команду детерминированно
(правило проекта «логи > догадки»), отбросил три гипотезы:

- *stdout-pollution от `--remote-components ejs:github`*: будто yt-dlp печатает
  download-строку перед JSON, и `split("\n")[0]` ловит не-JSON. Проверено
  холодным запуском с очищенным кэшем — stdout остаётся чистым однострочным
  JSON, парсится. Не причина.
- *первая загрузка remote-component (ejs)*: очистил `~/.cache/yt-dlp/`
  challenge-solver — холодный запуск всё равно успешен. Не причина.
- *гонка cookie-extraction при параллельных вызовах*: два одновременных
  `--cookies-from-browser firefox` — оба прошли. Лок реален, но редок;
  именно поэтому лечится ретраем, а не сериализацией.

Вывод: сбой **истинно транзиентный и не воспроизводится по команде** — поэтому
правильный фикс ретрай + видимая ошибка, а не «вычислить и устранить причину».
