# Knowledge: Ozon через browser MCP

Ozon-инструменты живут в **browser MCP** (`mcp/browser/index.js` +
`browser-extension/mcp-handlers.js`) и используют реальный браузерный профиль
пользователя: cookies, выбранный пункт выдачи, адрес доставки, авторизация,
избранное, покупки и заказы доступны так же, как в ручной Ozon-сессии.

Главный контракт для пользователя: если он спрашивает «найди товар, который я
покупал» или «что у меня в избранном», MCP должен вернуть **прямые ссылки на
товары**, а не только скриншотные карточки или номер заказа.

## Инструменты

- `ozon_search` — поиск по Ozon через query или готовый URL с фильтрами.
  Возвращает карточки товаров: title, direct URL, цена, рейтинг, отзывы,
  delivery labels, картинки, фильтры и варианты сортировки.
- `ozon_favorites` — читает избранное (`/my/favorites`) через тот же
  карточный parser.
- `ozon_purchases` — читает раздел «Покупки / Купленные товары». Без query
  стартует со специального списка `/my/favorites/list?list=4294967294`; с
  query использует `/my/purchases/search?text=...`.
- `ozon_orders` — читает список заказов (`/my/orderlist`) с пагинацией. Для
  поиска по названию товара должен открывать `orderdetails`, потому что список
  заказов сам по себе не всегда содержит названия и прямые товарные ссылки.
- `ozon_order_detail` — читает один `/my/orderdetails/?order=...` и возвращает
  товары внутри заказа: title, direct `/product/...` URL, цена, seller, images,
  статус, адрес и totals.

Сигнатуры публичных MCP-tools в `mcp/browser/index.js` обновляются только после
перезапуска MCP-сессии. Логика расширения hot-reload'ится, но новый tool name
не появится в уже инициализированной MCP-сессии без рестарта.

## Direct fetch без вкладки

Default path для Ozon — **не открывать вкладку вообще**. Service worker
расширения делает same-origin request:

```text
https://www.ozon.ru/api/composer-api.bx/page/json/v2?url=<path-and-query>
```

Запрос идёт с `credentials: include`, поэтому использует cookies текущего
браузерного профиля. Для этого в manifest/CSP должны быть разрешены
`https://www.ozon.ru/*` и `https://*.ozon.ru/*`. Это быстрее и безопаснее
фоновой вкладки: пользовательская вкладка не трогается, а Ozon видит обычную
авторизованную сессию.

Tab-transport остаётся только как fallback/debug (`transport:'tab'` или явный
`tabId`). Если всё же используется вкладка, handler обязан запомнить активную
вкладку и восстановить её после работы; навигация active tab во время фоновой
Ozon-работы запрещена. Восстановление должно возвращать вкладку внутри браузера,
но не фокусить окно через `chrome.windows.update({focused:true})`, иначе фоновый
Ozon fallback крадёт macOS-фокус у текущего приложения. Restore target должен
обновляться перед каждой навигацией fallback-вкладки: если пользователь сам
перешёл на другую вкладку во время job-а, нельзя возвращать его к старому
snapshot'у.

## Покупки не равны заказам

`/my/orderlist` отвечает на вопрос «какие заказы есть», но плохо отвечает на
вопрос «какой товар я покупал». В карточках заказов Ozon может показать статус,
дату, пункт выдачи и картинки, но названия товаров и прямые `/product/...`
ссылки живут в `orderdetails`. Поэтому `ozon_orders` подходит для статусов,
актуальных заказов и дат, а для товарного поиска он должен либо ходить в детали
каждого заказа, либо уступить `ozon_purchases`.

Для запроса вида «найди стаканчики / пергаментную бумагу» правильный источник —
раздел «Покупки»:

- sidebar «Купленные товары» ведёт на
  `/my/favorites/list?list=4294967294`; это карточный список купленных товаров,
  но на живом аккаунте он вел себя как список доступных к повторной покупке
  карточек и не равнялся всему счетчику «Покупки 416».
- free-text поиск по покупкам идёт через `/my/purchases/search?text=<query>`.
  Он возвращает полноценные карточки с названиями, картинками и прямыми
  ссылками на товары. Для пользовательских вопросов «какие стаканчики я
  заказывал» это основной режим.

Даты покупки в `/my/purchases/search` не являются надежной частью карточки.
Если пользователь просит «в этом месяце» или «последний заказ», нужен отдельный
этап корреляции с заказами/`orderdetails`, а не попытка угадать дату по карточке
покупки.

## Пагинация

Ozon использует разные механики пагинации для разных страниц; смешивать их
нельзя.

**Search/favorites/catalog.** Идём по paginator/next URL из Composer payload.
Если Ozon сам вернул `next_url`, надо использовать его как source of truth.

**`/my/purchases/search?text=...`.** Для поиска по купленным товарам следуем
только реальному paginator из ответа (`search_page_state`, `search_tiles_req`,
next URL и связанные параметры). Синтезировать cursor здесь нельзя: так легко
уйти в повторяющиеся страницы и получить timeout.

**`/my/favorites/list?list=4294967294`.** У специального списка купленных
товаров paginator может пропасть после первых страниц. Для него допустим
ограниченный synthetic cursor: брать последний SKU/id страницы как следующий
`page`, увеличивать `layout_page_index`, сохранять `start_page_id` и остальные
URL-параметры. Этот cursor **inclusive**: первый товар следующей страницы может
повторять последний товар предыдущей, поэтому дедуп по SKU обязателен. Стоп:
пустая страница, нет новых карточек или достигнут hard cap.

Шрам из сессии: подготовка URL не должна вычищать `page`,
`start_page_id` и `layout_page_index`. Если эти параметры потерять, ручная или
синтетическая пагинация возвращается на начало и кажется, что товаров всего 16-18.

## Парсинг карточек и матчинг запроса

Карточки приходят из Composer `widgetStates` (`tileGridDesktop` и соседние
виджеты). Нормализованный результат должен отдавать `title`, `url`, `price`,
`rating`, `reviews`, `delivery`, `images`, `sku/id` и raw text snippets для
диагностики.

Если у карточки нет валидной product-ссылки, `url` должен быть `null`, а не
`https://www.ozon.ru/`. Корневой URL выглядит как рабочая ссылка, но для
пользователя это мусор вместо товара.

Локальный query-фильтр после Ozon search должен быть мягким к русским формам:
достаточно full-phrase match или token/prefix match. Иначе запрос
«стаканчики» не матчится на title со словом «стаканы», а «пергаментную бумагу
для аэрогриля» не матчится на «Бумага (пергамент) для аэрогриля».

## Пользовательские симптомы

- «Ты нашел 18 заказов, а у меня их сотни» — почти всегда значит, что читается
  не тот источник: активные заказы, первый экран `/my/orderlist` или
  ограниченный список купленных товаров вместо поиска по «Покупкам».
- «На странице видно Покупки 416, а MCP нашел сильно меньше» — счетчик вкладки
  «Покупки» не равен количеству карточек, доступных в
  `/my/favorites/list?list=4294967294`. Для поиска конкретного товара используй
  `/my/purchases/search?text=...`.
- «Поиск зависает / timeout на второй странице» — проверь, не синтезируется ли
  cursor для `/my/purchases/search`. Для этой страницы нужен только реальный
  paginator из Ozon payload.
- «Ссылка ведёт на главную Ozon» — parser принял пустой href за товарную ссылку.
  Возвращай `url:null`, пока не найден настоящий `/product/...`.

## Проверенные живые запросы

На живом профиле поиск по покупкам через `/my/purchases/search` вернул прямые
товарные ссылки без открытия вкладок:

- `query="стакан"` нашёл бумажные стаканы 350 мл на 50 шт и 100 шт, включая
  прямые `/product/stakany-odnorazovye-bumazhnye-350-ml-.../` ссылки.
- `query="пергамент бумага аэрогриль"` нашёл бумагу/пергамент для аэрогриля,
  включая Lomberta 100 шт 20×20×4.5 см и другой размер на 110 шт.

Эти проверки важны не как fixture, а как sanity-check маршрута: если будущий
парсер снова отвечает только заказами или картинками без direct URL, он ушёл
не в тот источник.
