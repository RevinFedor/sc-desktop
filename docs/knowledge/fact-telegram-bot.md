# Knowledge: Telegram-бот SC Desktop

Telegram-бот является частью Electron main process, а не отдельным сервером.
Он стартует после готовности приложения, останавливается перед выходом и
показывает live-состояние рядом с кнопкой «Главная». Клик по status-pill
перезапускает bot service; renderer только отображает IPC snapshot, polling и
обработка ссылок всегда остаются в main process.

## Один token — один polling-процесс

Dev и production не являются разными ботами сами по себе: если оба читают один
`TELEGRAM_BOT_TOKEN` из общих настроек, они конкурируют за одну глобальную
очередь `getUpdates`. Сообщение получит тот экземпляр, который забрал update
первым; параллельный long polling также может получить Telegram conflict.
Поэтому с одним token одновременно должен работать только один SC Desktop.
Разделить dev/prod можно только разными bot token или явным env override.

На старте desktop отключает webhook и удаляет накопленные updates. Это
намеренный desktop-контракт: ссылка, отправленная пока приложение выключено,
не должна неожиданно запустить старую транскрипцию после следующего запуска.
После старта обрабатываются только новые сообщения.

## Доступ к боту

Если allowlist пуст и включён `claim_first_chat`, первое входящее сообщение
привязывает его chat id и выключает дальнейший auto-claim. После этого бот
отвечает только разрешённому chat/user id; новый случайный собеседник не может
запустить локальные jobs и потратить API-квоту владельца приложения.

Token хранится в общих настройках SC Desktop, но никогда не попадает в логи,
job parameters или документацию. Зелёный status-pill означает успешный
`getMe` и работающий polling, а не просто наличие строки token на диске.

## Instagram pipeline

Бот пока принимает только Instagram reel/post URL. Он не содержит отдельной
логики парсинга: после проверки allowlist вызывает тот же single-reel service,
что и paste-flow приложения. Поэтому cache lookup, выбранный
`transcribe_backend`, Android API session, Apify token и AI engine имеют один
source of truth. Бот не переключает Android API на Apify самостоятельно.

Цепочка одной ссылки:

1. Бот подтверждает приём и поддерживает Telegram `typing` во время job.
2. Single-reel service проверяет готовый sourceless/source-attached кэш и
   строит план строго из текущих Instagram-настроек.
3. При cache miss запускается обычный `ig_batch_transcribe`; bare URL остаётся
   sourceless job и при Android API использует `shortcode_session`.
4. Бот читает итоговый combined-файл и отправляет его содержимое в чат.

Прогресс может приходить отдельными служебными сообщениями. Финальный результат
объединяет метаданные и текст: `📸 <canonical URL>` и опциональный `Caption:`
идут обычным Markdown-текстом, затем транскрипт идёт одним code block в том же
сообщении. Строка `Instagram Reel · <shortcode>` наружу не отправляется.
Если escaped-текст превышает лимит Telegram, он делится только по неизбежному
лимиту платформы: метаданные остаются в первой части, следующие помечаются
`часть N/M` и каждая содержит отдельный code block.

## Ошибки и логи

Job с нулём сохранённых транскриптов и `item_error` имеет terminal status
`error`, даже если Python корректно завершил процесс с exit code 0. Иначе бот
получил бы ложный `done` без файла. Пользователь получает причину от первого
реального item error; отсутствие Android API-сессии и отклонённая Instagram
сессия не маскируются предложением запустить Apify.

Для причинной цепочки используются три тега production-лога:

- `[TelegramBot]` — update принят, job запущен, результат отправлен или rejected;
- `[InstagramReel]` — shortcode, выбранный backend, cache/owner и resolve mode;
- `[Jobs]` — worker start, `resolve_start`, item error и terminal status.

Сначала ищется первая строка сбоя в этой цепочке, и только после неё читается
код. Ошибка, которую бот лишь переслал пользователю, не считается первичной.
