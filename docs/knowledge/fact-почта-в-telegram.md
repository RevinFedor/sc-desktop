# Почта в Telegram: наблюдатель Gmail и сборка сообщения

Узкий канал «письмо от заданного отправителя → сообщение в Telegram». Использует
тот же бот-токен, что и уведомления Custom Terminal, но это отдельная подсистема
со своим источником, настройками и памятью о доставленном. Читает только тех
отправителей, которые перечислены явно; ящик целиком в Telegram не пересылается.

Продуктовый scope: уведомление о письме, а не почтовый клиент. Ответить,
переслать, пометить прочитанным нельзя — для этого есть ссылка «Открыть в Gmail».

## Rich Messages: почему не обычная отправка

Обычный `sendMessage` с `parse_mode` для писем непригоден по двум причинам сразу,
и обе выяснены на живом API, а не выведены из документации.

Первая — **любой неподдерживаемый тег отбивает всё сообщение**. Письма состоят из
`<div>`, `<table>`, `<span>`, инлайн-стилей и условных комментариев Outlook;
`parse_mode: HTML` понимает девять тегов и на первом же чужом возвращает
`can't parse entities`. Письмо не доходит вообще — не «приходит криво».

Вторая — **лимит 4096 символов**, в который среднее письмо не помещается.

`sendRichMessage` (Bot API 10.1, июнь 2026; блоки — 10.2, июль 2026) снимает обе:
неизвестные теги не роняют отправку, лимит 32768. Плюс появляется то, чего в
обычной отправке нет вообще — блок `<details><summary>`, сворачивающий тело
письма под тап.

Проверенные границы (ответы живого API, не догадки):

| Ситуация | Ответ |
|---|---|
| `<script>`, `<table>`, `<!--[if mso]>`, незакрытые теги | принимается, не падает |
| текст > 32768 | `RICH_MESSAGE_TEXT_TOO_LONG` |
| пустая строка / только пробелы | `RICH_MESSAGE_EMPTY` |
| `<details>` без текста внутри | `RICH_MESSAGE_EMPTY` |
| пустой `html` | `RICH_MESSAGE_HTML_INVALID` |

Прочие лимиты из документации: 500 блоков, 16 уровней вложенности, 50 медиа.
Ограничение блоков достигается раньше лимита символов на письме из сотен коротких
абзацев — поэтому обрезка сторожит оба счётчика, а не только длину.

**«Не падает» ≠ «выглядит хорошо».** Мусорный HTML письма проходит, но
table-вёрстка схлопывается в одну ячейку-кашу. Это и есть причина, по которой
письмо пересобирается (ниже), а не отдаётся Telegram как есть.

## Сборка сообщения

Две строки: тема со временем (видна в ленте) и раскрывающийся блок со всем
остальным. Внутри блока — адрес отправителя, тело письма, ссылка «Открыть в Gmail».

Ссылкой становится **не вся строка заголовка, а имя отправителя внутри неё**:
из домена вырезается название (`codexresets.com` → `codexresets`), ищется в теме
без учёта регистра и подсвечивается только оно. Не нашлось — ссылка уезжает в
конец строки отдельным `· домен`. Причина в `methodology/переносимый-дизайн.md::Ссылка живёт на смысловом слове`.

Имя отправителя из шапки убрано намеренно: когда тема уже содержит то же слово,
`Codex Resets · noreply@codexresets.com` — третий повтор подряд. Показывается
только если добавляет смысл («Бухгалтерия · billing@…»).

**Свёрнутая строка ищет смысл, а не берёт первую строку письма.** Письма
начинаются с ASCII-рамки, логотипа или «view in browser» — такой заголовок
бесполезен. Строка-кандидат обязана содержать минимум два слова с буквами после
вычёркивания псевдографики. Разделители из подчёркиваний и решёток вырезаются
только группами (`====`), иначе `subscription_request` теряет подчёркивание.

## Разбор письма

DOM-парсер здесь вреден: почтовый HTML часто невалиден, и строгий парсер либо
падает, либо теряет текст. Разбор идёт потоком по тегам.

**Стиль накапливается счётчиками вложенности, а разметка синтезируется заново.**
Это неочевидно и важно: письмо вида `<b>жирный <i>оба</b> курсив</i>` (закрытие
не в том порядке) при копировании тегов даёт рассогласованную кашу, которую
Telegram отвергнет. Синтез из состояния делает такой результат невозможным
структурно — каждый кусок текста знает свой набор стилей, теги рождаются заново.
Первая версия копировала теги из письма и ловила ровно этот баг.

Что ещё делает разбор:

- **ячейки таблицы склеиваются пробелом**, не переводом строки — иначе
  «Метрика | 42 ms» рассыпается в столбик из огрызков;
- **трекинг-ссылки разворачиваются** в настоящий адрес из параметров `url`, `u`,
  `redirect` и подобных — пользователь видит, куда идёт;
- **`javascript:` и `data:` отбрасываются**, текст ссылки сохраняется;
- **`<script>`/`<style>`/`<form>` выбрасываются вместе с содержимым**, счётчик
  вложенности не даёт вложенному `</script>` внутри строки оборвать выброс раньше;
- **`>` в начале строки становится цитатой** — в письмах цитата чаще нарисована
  текстом, чем тегом;
- **псевдографика и отступы уходят в моноширинный блок** — иначе рамки разъедутся.

Обрезка длинного письма режет тело, а не шапку: заголовок обязан дойти всегда.

## Доступ к почте

Выбран **пароль приложения** (16 символов, `myaccount.google.com/apppasswords`),
а не OAuth. Обоснование, которое не выводится из кода:

- OAuth требует своего проекта в Google Cloud и **обязательного `Publish app`** —
  в режиме `Testing` токен умирает ровно через 7 дней. Это самая массовая жалоба
  по теме; неверный статус проекта ломает интеграцию через неделю после настройки;
- чужой уже верифицированный клиент (например, из gcloud) использовать нельзя —
  Google отвечает `redirect_uri_mismatch`;
- цена пароля приложения: **доступ ко всему ящику, ограничить «только чтение»
  нельзя** — у этого способа нет областей доступа. Умирает при смене основного
  пароля. Если в аккаунте страница паролей недоступна («настройка недоступна для
  вашего аккаунта») — остаётся только OAuth.

Пароль лежит в общем `~/.config/sc/settings.json` (секция `mail`), файл закрыт
режимом `0600`.

## Наблюдатель

Постоянное IMAP-соединение, реакция на письмо около секунды. Опрос раз в минуту
оставлен подстраховкой на случай потерянного уведомления; молчащее соединение
Gmail закрывает сам, поэтому раз в 20 минут отправляется `NOOP`.

**Обрыв — штатное событие, не ошибка.** Сон ноутбука, смена сети, таймаут на
стороне Gmail: переподключение с нарастающей паузой до 5 минут. Исключение —
неверный пароль: повтор бессмысленен, наблюдатель останавливается со статусом
`auth_failed`.

**Отбор отправителей делается на своей стороне, а не поиском на сервере**:
серверный поиск по нескольким отправителям хрупок и по-разному ведёт себя с
алиасами. Правило — точный адрес или домен вида `@github.com`; проверка идёт по
окончанию строки с ведущей `@`, поэтому `evil@notgithub.com` не проходит.

**Первый запуск не рассылает историю.** Иначе включение обернётся пачкой
уведомлений о вчерашних письмах. Признак «этот ящик уже осматривали» хранится
отдельно от списка доставленных — без него каждый перезапуск считался бы первым
знакомством, и новые письма молча пропадали бы навсегда. После простоя досылаются
письма за последние 15 минут. Общий принцип —
`methodology/переносимый-дизайн.md::Первый запуск наблюдателя не рассылает историю`.

Память о доставленном (последние 500 писем) переживает перезапуск, поэтому одно
письмо не приходит дважды.

## Отказ доставки не молчит

Если Rich Message не собрался из-за неожиданной разметки, уходит короткое обычное
уведомление с темой и отправителем. Молчание хуже урезанного сообщения: письмо
могло быть важным, а пользователь не узнает, что оно вообще было.

Временные отказы Telegram (429, 5xx, сеть) повторяются до четырёх раз с
нарастающей паузой и учётом `retry_after`. Постоянные (чат не найден) — пишутся в
лог и не роняют приложение.

## Проверка без внешних сервисов

Письмо кладётся **прямо в ящик** через `IMAP APPEND` — это не отправка почты, а
запись в папку, как при доставке настоящего письма. Дальше оно проходит весь путь
как обычное: наблюдатель замечает → конвертер разбирает → бот присылает. Никаких
песочниц вроде Mailtrap и никаких писем самому себе через внешний сервер.

Это возможно только потому, что доступ даёт право на запись (у пароля приложения
оно есть всегда). При переходе на OAuth с `gmail.readonly` такая проверка
перестанет работать — понадобится либо область `gmail.insert`, либо настоящая
отправка через внешний сервер.

После проверки тестовое письмо удаляется поиском по его идентификатору.

## Настройки

Секция `mail` в `~/.config/sc/settings.json`: включение, чат, список отправителей,
подмена адреса сайта для домена, учётные данные почты. Добавить отправителя —
дописать строку в `senders`.

Наблюдатель работает, **пока запущено SC Desktop**. Приложение закрыто — письма
не приходят; при следующем запуске догоняются только свежие.

В dev-режиме доставка выключена, включается через `SC_MAIL_NOTIFY_DEV=1` — иначе
отладочный запуск шлёт реальные сообщения в личный чат.
