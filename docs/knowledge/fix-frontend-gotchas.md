# Knowledge: Frontend Gotchas

Подборка ловушек, которые пришлось дебажить по симптому. Каждая — workaround вокруг чужого поведения (React JSX, Vite watcher, async React state, `useSyncExternalStore`). Описание здесь чтобы при следующем встрече похожего симптома сразу понять что пробовать.

---

## 🪤 JSX `&& 0` с SQLite integer колонками

**Симптом:** под каждым текстовым сообщением Telegram-канала в `ChatView` стоит цифра `0` отдельной строкой. Маленькая, серая, без контекста — выглядит как баг рендера или обрезанный лейбл.

**Корневая причина:** SQLite колонка `items.has_media` объявлена как `INTEGER NOT NULL DEFAULT 0` — better-sqlite3 возвращает её как **число `0`/`1`**, а не boolean. В JSX:

```js
const noFile = !isYoutube && item.has_media && !item.media_path
//                            ↑ 0 (число), не false
//   true && 0 && true === 0  ← && короткое замыкание возвращает 0
//   {0 && <div>...</div>}    ← React рендерит литеральный "0"
```

Это **известная React gotcha**: JSX рендерит truthy-всё-кроме-false-null-undefined, а **0 рендерится как строка `"0"`** (потому что число — валидный child).

**Решение:** coerce в boolean везде где значение приходит из SQLite-integer column:
```js
const noFile = !isYoutube && !!item.has_media && !item.media_path
```

Или: `Boolean(...)`, или явное `> 0`/`!= null`. Не полагаться на `&&` truthiness когда левая часть — number.

**Где ещё может стрельнуть:** `items.has_media`, `items.views`, `items.likes`, `items.comments`, `items.duration_seconds`, `items.transcribe_cost_usd`, `jobs.cost_usd`, `jobs.items_failed` — все integer/real колонки, которые могут быть валидными нулями.

**Текущие места проверены и исправлены** в этой сессии: `ChatView::noFile`, `ActivityPanel::JobRow` (items_done/items_total counter), `JobDetail::YoutubeBody` (cost_usd, duration_sec). При следующем добавлении проверки SQLite-bool полей — сразу `!!` или `Boolean()`.

## 🪤 Vite full-reload от cli-tools WAL файлов

**Симптом:** при клике на «Telegram → сессии» в Library:
- DevTools panel мигает (вкладка Elements ↔ Console самопроизвольно переключается).
- Юзер «улетает» на Home — то есть текущий screen сбрасывается на paste.
- В `logs/dev.log` чистый `[Startup]` + `[DB] opened` — никаких ошибок.
- В Vite output ничего подозрительного.

**Что происходит на самом деле:**
1. UI открывает `tg-settings` → IPC `tg:listSessions` → spawn `tg_sessions_ndjson.py list`.
2. Скрипт коннектится к **обеим** `*.session` через `TelegramClient(...).connect()` для проверки `is_user_authorized`.
3. Telethon — это sqlite БД. Connect создаёт WAL-файлы: `session.session-wal`, `session.session-shm` рядом.
4. **Vite-watcher следит за project root** (с тех пор как `cli-tools/` переехал внутрь sc-desktop).
5. Mutation в `cli-tools/telegram/session.session-wal` → Vite думает «исходник изменился» → **full reload renderer'а**.
6. Renderer перезапускается → in-memory store сбрасывается на initial → `screen = { name: 'paste' }` = Home.
7. DevTools переподключается к новому renderer'у — отсюда мигание.

**Корневая причина:** project root содержит non-source поддиректорию (`cli-tools/`) с файлами, которые мутируются runtime'ом без участия пользователя. Default Vite watch это не знает.

**Решение:** `vite.config.js`:
```js
server: {
  watch: {
    ignored: [
      '**/cli-tools/**',          // python + Telethon WAL
      '**/logs/**',                // Electron app log rotation
      '**/dist/**',                // build artifacts
      '**/.semantic-index.json',   // regenerated by docs_search index
    ],
  },
}
```

**Где ещё стрельнёт:** любая будущая Python-операция которая трогает sqlite через Telethon, или любой long-lived process который пишет в файлы внутри project root. Если добавляется новая корневая папка с runtime-mutable файлами — её **обязательно** в `ignored`.

**Альтернатива которую отбросили:** держать cli-tools/ снаружи project root (как было). Усложняет распространение (нужно копировать две папки), а cli-tools — это часть продукта sc-desktop. Один корень предпочтительнее.

## 🪤 ChatView infinite scroll: race на async setLoading

**Симптом:** React warning в консоли «Encountered two children with the same key, `100`. Keys should be unique...». В UI — дублированные сообщения в чате (одно и то же сообщение несколько раз подряд).

**Что происходит:**

`ChatView` использует infinite scroll через `IntersectionObserver`. Гард на конкурентные запросы был через React state:

```js
const loadPage = useCallback(async () => {
  if (loading || exhausted) return       // ← guard
  setLoading(true)                       // ← async, не отражается мгновенно
  // ... fetch + setItems
  setLoading(false)
}, [loading, ...])
```

Race происходил так:
1. Mount → `useEffect` инит-загрузки → `loadPage()` (T1). `setLoading(true)` — но state ещё не закоммичен.
2. На том же тике IntersectionObserver mount'нулся, sentinel сразу виден → `loadPage()` (T2).
3. T2 проверяет `loading` — он всё ещё `false` (closure-stale + state batching).
4. Оба запроса стартуют с **одинаковым offset=0** → возвращают одну и ту же страницу.
5. `setItems(prev => [...prev, ...rows])` дважды — дубли по `id`.
6. React видит duplicate keys → warning.

**Корневая причина:** `setLoading` в React 18 пакуется в batch и не отражается **синхронно**. Между `setLoading(true)` и rerender пройдёт >0ms — за это время может пройти второй вызов из другого источника, и его guard всё ещё видит `loading === false`.

**Решение:** synchronous guard через `useRef`:
```js
const inFlightRef = useRef(false)

const loadPage = useCallback(async () => {
  if (inFlightRef.current || exhausted) return
  inFlightRef.current = true
  setLoading(true)  // оставляем для UI спинера
  try {
    // ... fetch
  } finally {
    inFlightRef.current = false
    setLoading(false)
  }
})
```

`useRef` мутируется **синхронно**, второй вызов сразу видит `true` и выходит. `loading`-state остаётся для рендеринга «Loading…», но не используется как guard.

## 🪤 «Cannot update a component while rendering» из functional updater

**Симптом:** в DevTools-консоли warning *«Cannot update a component (`PasteScreen`) while rendering a different component»*. Никаких видимых багов — просто шум, который копится при каждом keystroke в input.

**Что происходило:** в PasteScreen раньше был такой setter:

```js
function setValue(v) {
  setValueLocal(v)
  setPasteState({ value: v })   // ← пишет в global store, эмитит подписчикам
}

function setCommitted(next) {
  setCommittedLocal(prev => {
    const resolved = typeof next === 'function' ? next(prev) : next
    setPasteState({ committed: resolved })   // ← эмит из functional updater
    return resolved
  })
}
```

`setPasteState` в нашем мини-store вызывает `subs.forEach(fn => fn())` — пробуждает все `useSyncExternalStore`-подписчики. Если этот эмит происходит **внутри functional updater** (`prev => ...`), React отрабатывает его в фазе reducer'а — а в этот момент любой другой подписчик может всё ещё рендериться. Отсюда warning.

**Решение:** убрать запись в store из самого setter'а, делать её через `useEffect` после коммита:

```js
const setValue = setValueLocal     // pure local
const setCommitted = setCommittedLocal

useEffect(() => {
  setPasteState({ value, committed })  // emit ПОСЛЕ render
}, [value, committed])
```

Локальный state остаётся быстрым (keystroke не дёргает store), а зеркалирование в store происходит когда React уже всё закоммитил — никаких subscriber-callback'ов в render-фазе.

**Где ещё может стрельнуть:** любой setter, который из functional-updater пишет в кастомный store с synchronous emit'ом. Подписки через Redux/Zustand работают корректно потому что у них batched scheduler — наш store наивный (`subs.forEach`), поэтому emit нужно **выносить из render-фазы вручную**.

## 🪤 JSX-комментарий с `*/` внутри ломает Vite-парсер

**Симптом:** Vite валит билд с ошибкой `Expected corresponding JSX closing tag` или подобной непонятной — указывая на строку **после** комментария, не на сам комментарий. В DevTools-консоли HMR не подхватывается, страница белая.

**Что происходило:** в JSX-комментарии я написал что-то вроде:

```jsx
{/* TikTok jobs share the YT body shape (entity_title/file_path/yt*
    ↔ tk*). The bodies read job.tk*/yt* both ... */}
```

Последовательность `tk*/yt*` содержит `*/` — JSX-парсер закрывает комментарий **на нём**, а не на финальном `*/`. Дальше всё что справа интерпретируется как обычный JSX → синтаксическая ошибка где-нибудь снизу.

**Решение:** не использовать `*/` (или `/*`) в JSX-комментариях. Заменять на словесную запись:

```jsx
{/* TikTok jobs share the YT body shape — bodies read both job.tk and
    job.yt fields, so we mirror tk → yt before passing in. */}
```

Не путать с обычными JS-комментариями: `// tk*/yt*` в коде валиден, проблема **только** в `{/* ... */}` JSX-форме.

**Где ещё может стрельнуть:** любой комментарий со звёздочками рядом со слешами — regex-паттерны, glob-выражения (`*.js`/`*.tsx`), markdown-ссылки на файлы. При написании JSX-комментария глазами ищи `*/` внутри — если есть, перефразируй.

**Defensive layer:** также добавил dedup при `setItems` по `id`:
```js
setItems(prev => {
  const seen = new Set(prev.map(it => it.id))
  const fresh = rows.filter(r => !seen.has(r.id))
  return [...prev, ...fresh]
})
```

Это страховка на случай если race всё-таки проскочит (например, в React Strict Mode dev double-invoke effects). Filtration линейная, на 100 items безразлично, но дубль-keys больше не появится.

**Pattern для будущего:** любой in-flight guard через **state** — потенциальная race. Если guard критичен (нельзя дважды стартовать) — `useRef` синхронный, `useState` для UI-индикации. Не путать.

## 🪤 `useSyncExternalStore` + `arr.filter()` = infinite render loop

**Симптом:**
```
Maximum update depth exceeded. This can happen when a component repeatedly
calls setState inside componentWillUpdate or componentDidUpdate.
   at forceStoreRerender (chunk-NXESFFTV.js:12047)
   at updateStoreInstance (chunk-NXESFFTV.js:12023)
The above error occurred in the <TelegramScreen> component
```

Юзер видит белый экран / краш React Error Boundary при первом рендере экрана, который зовёт `useSources('telegram')` (фильтрованный вариант).

**Причина:** `useSyncExternalStore` сравнивает результат `getSnapshot` через `Object.is`. Если `getSnapshot` каждый раз возвращает **новый массив** с тем же содержимым (как делает `arr.filter(...)`) — React видит «snapshot изменился» → планирует rerender → опять новый массив → loop.

```js
// ❌ так было в src/lib/sources.js:
return useSyncExternalStore(
  fn => { subs.add(fn); return () => subs.delete(fn) },
  () => {
    const all = snapshot()
    return platform ? all.filter(s => s.platform === platform) : all  // ← новый array на каждом вызове
  },
  () => snapshot(),
)
```

**Фикс — мемоизация `(src, platform) → out`:**
```js
const filterCache = new Map()   // platform -> { src, out }

export function useSources(platform = null) {
  init()
  const getSnapshot = () => {
    const all = snapshot()
    if (!platform) return all
    const cached = filterCache.get(platform)
    if (cached && cached.src === all) return cached.out
    const out = all.filter(s => s.platform === platform)
    filterCache.set(platform, { src: all, out })
    return out
  }
  return useSyncExternalStore(subscribe, getSnapshot, getSnapshot)
}
```

Кэш инвалидируется автоматически — как только `refresh()` заменяет `sources` на новый массив, ссылка `cached.src !== all`, пересчитываем filter один раз.

**Pattern:** любой `useSyncExternalStore` с `getSnapshot` который **трансформирует** базовый snapshot (filter / map / pick) обязан мемоизировать результат относительно identity исходного. Базовый `getSnapshot` который возвращает сам store — безопасен (ссылка стабильна между неинвалидированными моментами).

**Чек при добавлении нового selector-аргумента в кастомный store:** *«если я вызову getSnapshot два раза подряд без изменения store — вернётся ли точно та же ссылка?»*. Да → ок. Нет → нужен кэш.

> **Что пробовали и почему не помогло:** `useMemo(() => filtered, [sources, platform])` снаружи. Не помогает — `useSyncExternalStore` зовёт getSnapshot **внутри своего цикла подписки**, до того как `useMemo` успевает сработать на новом render-цикле. Кэш должен жить **в самом getSnapshot**, на module-level или через ref.
